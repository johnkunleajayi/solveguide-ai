# SolveGuide AI

Understand the question. Find the answer. Learn why.

SolveGuide can **CAPTURE -> UNDERSTAND -> RECOMMEND -> EXPLAIN** when its local
backend and configured providers are available. Milestone 5 adds an explicit,
structured educational recommendation from QuestionObservation. Vision extraction
and answering remain separate operations; neither paid stage runs automatically.
Recommendations and confidence are estimates, not guarantees of correctness.
Milestone 6 adds PostgreSQL-backed Google identity and server-side sessions around
that pipeline. Signing in never saves captures, questions or answers.

## Architecture: a modular monolith

```text
Windows Graphics Capture / Direct3D11
  -> Rust capture module -> typed CaptureResult -> React capture preview
  -> explicit Read Question -> local FastAPI -> VisionService
  -> VisionProvider -> OpenAIVisionProvider -> QuestionObservation -> desktop UI
  -> explicit Get Suggested Answer -> AnswerService -> AnswerProvider
  -> OpenAIAnswerProvider -> AnswerRecommendation -> suggested answer + explanation
```

- `src/App.tsx`: shell, modal visibility, theme and pointer preferences.
- `src/capture/`: existing native capture contract, adapter and state machine.
- `src/vision/`: observation types/runtime guard, HTTP client and cancellable state.
- `src/answer/`: answer contract/runtime validation, text-only HTTP client, request state
  and synchronous capture/observation lifecycle invalidation.
- `AnswerRecommendationView.tsx`: separate recommended options/response, explanation,
  answer confidence, warnings and explicit request/retry/cancel controls.
- `CaptureDialog.tsx`, `CapturePreview.tsx`: selection, preview and explicit reading action.
- `QuestionObservationView.tsx`: prompt, instructions, options, context, visuals and warnings.
- `src/styles/`: Neutral Light tokens and focused, reusable presentation styles.
- `src-tauri/src/capture/`: Windows discovery, validation and single-frame capture.
- `backend/app/config.py`: backend-only pydantic-settings configuration.
- `backend/app/schemas.py`: strict request and observation models.
- `backend/app/images.py`: bounded in-memory PNG decoding/validation.
- `backend/app/providers/base.py`: `VisionProvider` protocol, with one `observe` operation.
- `backend/app/providers/openai.py`: official async OpenAI SDK Responses API adapter.
- `backend/app/service.py`: provider-independent orchestration and output revalidation.
- `backend/app/api.py`, `middleware.py`, `main.py`: routes, request bounds, origins,
  dependency injection, safe error envelopes and application factory.

The provider contracts support future alternatives without coupling routes or React
to OpenAI. Only OpenAI is implemented. `backend/app/answer/` contains separate
schemas, provider protocol, centralized prompt, OpenAI adapter, deterministic service
and API route. No microservice, OCR engine or retrieval is introduced by vision;
authentication/database infrastructure is described in Milestone 6 below. No
Context Library or history is implemented.

## Capture and Read Question

Analyze Question opens capture preparation. Screen and Window require an explicit
source choice. Region is a typed, visibly unavailable option; no region capture
is implemented. Monitor inventory includes dimensions, desktop position and primary
status. Windows are filtered for visibility/minimization/cloaking/tool/untitled/system
and SolveGuide-owned windows. Native opaque tokens are revalidated before capture.
No frontend-supplied paths or HWNDs are accepted. An unchanged source retains its
token across source refresh so cancellation does not break Retake.

Capture acquires one frame off the UI thread, with a five-second frame wait and
40-megapixel bound. SolveGuide hides briefly for monitor capture and restores on
success/failure. Windows are captured as window surfaces, never via a fallback crop
of overlapping desktop content. The OS capture indicator is retained. Preview
reports actual content dimensions, which can differ from discovery bounds due to
invisible Windows borders. Retake, Change Source and Clear capture remain available.

Capture itself uploads nothing. The separate **Read Question** action explicitly
sends the current PNG to the local backend and then OpenAI. The UI states this before
the action. Reading has progress, Cancel and explicit Retry states. Retake/Clear
invalidate observation state and abort the client request; late replies are ignored.
Cancellation cannot guarantee that a provider request already accepted by OpenAI
will stop or avoid charges. No automatic retry or background reading occurs.

## API and QuestionObservation

`POST /api/v1/vision/question` accepts JSON with only:

```json
{ "media_type": "image/png", "image_base64": "<base64 PNG bytes>" }
```

No paths, remote URLs, source/window titles or filesystem references are accepted.
The streaming JSON body is capped at 14 MiB before parsing; decoded PNG at 10 MiB
and 40 megapixels. MIME type, base64, PNG structure, frame count and actual decoder
are checked. Only one vision request runs at a time; parallel work returns busy.
Malformed input is rejected without echoing sensitive validation input.

A strict `QuestionObservation` contains:

| Field | Meaning |
| --- | --- |
| status | detected, unclear or no_question |
| question_type | multiple_choice, multiple_select, true_false, short_answer, essay, mathematics, code, mixed or unknown |
| question_text | Complete visible prompt or nullable partial/absent text |
| options | Visible label/text pairs, with no correctness/recommendation field |
| instructions | Relevant visible task instructions |
| required_selection_count | Explicit count when established by the image; otherwise null |
| visible_context | Supporting question content, excluding unrelated application chrome |
| visual_elements | Typed chart/diagram/table/screenshot/illustration/formula/code/other descriptions, optional visible text and code language |
| extraction_confidence | Bounded reading-quality estimate; not calibrated certainty or answer confidence |
| warnings | Uncertainty, cropped/obscured content or incomplete extraction |

The adapter uses `responses.parse(..., text_format=QuestionObservation)` and validates
the parsed result again. It handles refusal, incomplete/malformed output, auth,
quota/rate limits, connectivity and timeout errors. Screenshot instructions are
untrusted data, not instructions to the provider. Math notation and code indentation
are preserved where legible. No question is forced into MCQ and missing text is not
invented. The schema rejects extra fields, including answer/reasoning fields.

Errors use `{ "error": { "code": "...", "message": "..." } }` with safe messages.
`GET /api/health` reports process availability and provider configuration presence,
never credentials. Successful no-question/unclear results are observations with
review guidance, not fabricated successes or answers.

## Privacy and image lifecycle

Capture -> process-memory preview -> explicit Read Question -> bounded in-memory
backend validation -> configured OpenAI provider -> structured observation -> UI.
The backend never saves the image, creates history, uploads a Files API object,
logs base64/text/observations or stores data in a database. Request image buffers
become unreachable after completion. Logs contain only allowlisted event metadata
(request ID, outcome code and duration); SDK/HTTP debug logging is suppressed.
Response caching is disabled. Only appearance and Pointer Light preferences persist.
Clear/reload/exit release current UI capture/observation references. There is no
secure-memory-wipe promise; normal OS pagefile/crash policies remain external.

OpenAI receives the image only on Read Question. `store=False` disables response
application storage; it is not a promise of zero provider retention. The account's
OpenAI data controls and provider policies still apply. Keep sensitive material out
of controlled tests. Never enable raw request tracing or SDK debug payload logging.

## Milestone 5: structured educational recommendations

### Separate answer architecture

VisionProvider answers "What is the question?" and continues to return only
QuestionObservation. AnswerProvider answers "What is the best response, and why?"
from that validated observation. The normal reasoning request contains no screenshot,
CaptureResult, image bytes, file path or remote image URL. There is no combined
vision-and-answer prompt and no automatic answer request when reading completes.

`AnswerProvider.recommend(QuestionObservation)` is a provider-independent protocol.
`OpenAIAnswerProvider` uses the official async SDK Responses API with strict Pydantic
structured output, validates it again, and exposes only the public recommendation.
`AnswerService` gates inadequate input and applies deterministic cross-validation
against the original observation. Routes depend on the service/provider boundary;
React never imports the SDK or accesses credentials. This remains one FastAPI
modular monolith, not another service.

Files are grouped under `backend/app/answer/`: `provider.py`, `openai.py`, `prompt.py`,
`schemas.py`, `service.py`, `api.py`, `errors.py`. Existing capture and vision modules
remain in place. `src/answer/` contains the matching typed client/controller and
runtime guard; `src/styles/answer.css` composes existing design tokens.

### Answer endpoint and contract

`POST /api/v1/answer` accepts the QuestionObservation object directly as its JSON
body, not a wrapper and not a screenshot. Unknown input fields (including image
payloads) fail validation. It shares the existing loopback, Origin, host, no-store,
structured-error and sanitized-logging boundaries. The streamed answer body is
bounded to 256 KiB. Vision retains its existing PNG/14 MiB body limits. A single
shared in-flight slot prevents overlapping paid vision/answer operations.

Strict `AnswerRecommendation` fields:

| Field | Meaning |
| --- | --- |
| status | answered, uncertain, insufficient_information or unsupported |
| question_type | Must match the input QuestionObservation type |
| selected_options | Unique existing option labels, never invented IDs |
| answer_text | Nullable concise direct answer/thesis/response, plain text |
| true_false_answer | Nullable boolean for natural true/false responses |
| code_answer | Nullable typed language/code block preserving whitespace |
| explanation | Concise public educational rationale, not private chain-of-thought |
| key_points | Up to eight concise supporting points or public calculation steps |
| confidence | Answer confidence in [0,1], independent from extraction confidence |
| warnings | Ambiguity, limitations or reasons to review/abstain |

Unknown output fields, duplicates, blank response text and inconsistent abstentions
are rejected. The service rejects mismatched question types, nonexistent labels,
wrong selection counts and inconsistent true/false labels/booleans. Invalid results
become structured errors; there is no silent count/label correction and no automatic
paid retry. The client also validates the response before rendering it.

### Question-type behavior and uncertainty

- MCQ: exactly one observed label, a direct response and useful explanation. A
  contradictory known selection count causes an insufficient-information result.
- Multiple-select: existing unique labels and the exact required count when known.
  An unknown count stays unknown; no artificial single-choice limit is imposed.
- True/false: a clear boolean without requiring artificial A/B options. When visible
  choices exist, their selected label must be valid and agree with recognizable
  True/False text.
- Short answer: direct response first, then concise explanation.
- Essay: a concise thesis/response and supporting points, with no meaningless labels
  or enormous essay by default.
- Mathematics: a clear final result and concise educational explanation/key steps,
  preserving notation. No hidden reasoning traces are requested, returned or stored.
- Code: actual question/language context comes from the observation; typed code blocks
  preserve indentation. Provider HTML is escaped text and is never executed.
- Mixed: uses all structured prompt/context/visual descriptions; missing necessary
  information should produce insufficient_information rather than invented content.
- Unknown: deterministic unsupported status without a provider call.

No-question, unclear or missing prompt input, contradictory single-choice selection
instructions, and inadequate visible options produce deterministic abstentions
without paid requests. Uncertain provider responses require warnings; a tentative
selection still must satisfy label/count validation. Insufficient/unsupported results
contain no answer, selections, code, key points or answer confidence (confidence=0).

Reading/extraction confidence estimates what was seen. Answer confidence estimates
correctness of the recommendation. The observation and recommendation remain distinct
UI sections; neutral observed options are not overwritten or highlighted as correct.
Percentages can coincidentally match, but are separate values and are not statistically
calibrated probabilities. High extraction confidence does not prove answer correctness.

### Explicit requests, state and presentation

Capture -> Read Question -> review QuestionObservation -> **Get Suggested Answer**.
The answer is visually emphasized above its explanation. Multiple-select shows all
recommended labels; essay shows Suggested response; math shows explanation/key steps;
code uses an accessible escaped code block. Warnings/abstentions are visible states.

Get Suggested Answer is enabled only after a ready observation with a capture preview.
Each intentional click can incur provider charges. Loading blocks duplicate submission;
Cancel recommendation aborts client transport and ignores late responses. **Try Again**
is a new explicit attempt after a failure or an existing recommendation. It is not an
automatic retry. SDK retries are disabled. Cancelling a request already received by
OpenAI cannot guarantee cancellation or avoid charges.

Retake, Change Source, Clear and reading a new observation synchronously invalidate
recommendations and abort pending answer requests. Opening Change Source invalidates
an answer even when its old capture remains available or selection is cancelled.
Generation guards prevent an old response from reappearing against a new question.
Cleanup releases listeners and current in-memory state; no answer history is retained.

## Milestone 6: authenticated platform foundation

The user's stable baseline `cdc54ca` includes manually validated Milestones 3–5.
Milestone 6 adds shared identity/session infrastructure, not saved learning content.
Google/Neon live setup and real login require your configuration and manual verification.

### Modules and database

`app/database.py` owns SQLAlchemy 2 async engine/session creation, a declarative base,
bounded connection pool, transaction dependency and sanitized database errors.
It uses Psycopg 3 async with PostgreSQL; a normal `postgresql://` or
`postgresql+psycopg://` URL works, including Neon. URL credentials use SecretStr.
`app/runtime.py` explicitly selects a selector event loop on Windows because Psycopg
async cannot use Windows' default proactor loop. Both the backend script and Alembic
use this loop factory. Pool resources close at application shutdown. Request
transactions commit on success, roll back on failure and release their connections.
No startup `create_all()` or SQLite fallback exists.

`app/auth/` separates models, public schemas, randomness/hash helpers, Google OIDC
adapter, session/OAuth services, current-user dependencies, HTTP boundaries and routes.
Only three tables exist:

| Table | Purpose and constraints |
| --- | --- |
| users | Internal UUID; unique Google subject; normalized, indexed email; verified flag; display name; optional avatar; timezone-aware created/updated/last-login timestamps |
| auth_sessions | UUID; cascading user FK; unique SHA-256 credential hash; created/expiry/last-seen/revocation timestamps; positive-lifetime constraint |
| oauth_attempts | Short-lived state/binding hashes; nonce; encrypted PKCE verifier; desktop/web transport; bounded lifecycle; optional user FK; expiry index |

Google subject is the identity key. Email is not an account-linking key and is not
globally unique. A PostgreSQL upsert handles concurrent logins for the same subject.
Sessions contain 32 random bytes encoded as opaque URL-safe credentials. Only their
SHA-256 hashes enter PostgreSQL; high-entropy secrets are not passwords and need no
password hash. Sessions expire after 168 hours by default (configurable 1–720 hours),
support revocation/logout and update last-seen on authenticated lookup. Google access,
refresh and ID tokens are never stored. Expired OAuth rows are pruned on later starts;
the verifier is cleared on completion/failure/cancellation. A maintenance retention
policy for expired auth records can be added when deployment requirements are known.

### Google flow and desktop transport

1. The explicit Settings **Sign in with Google** action invokes the main-window-only
   native auth command. Rust requests a short-lived transaction from the backend.
2. Backend generates independent random state, nonce, PKCE verifier and exchange
   binding; stores state/binding hashes and a Fernet-encrypted verifier for ten minutes.
3. Rust retains the exchange secret in memory and opens only the allowlisted Google
   HTTPS authorization endpoint using Windows' normal browser. No embedded Google login.
4. Google returns an authorization code to the exact configured backend callback.
   State is claimed under a PostgreSQL row lock and committed before token exchange,
   preventing replay even if the provider fails. The backend redeems with PKCE.
5. Authlib/joserfc verify the RS256 signature using Google's fixed JWKS endpoint,
   issuer, audience, expiry/issued-at, nonce and applicable OIDC claims. Unverified
   email is rejected. Identity is derived from the verified token, never frontend fields.
6. Callback records a ready transaction without putting a session credential in a URL.
   The native app polls at two-second intervals while signing in, for at most ten minutes.
   A one-time exchange under a row lock issues a server-side session. Replays fail.
7. Rust keeps the opaque session only in process memory and attaches it to fixed
   loopback auth requests. React receives only public user DTOs. No auth data enters
   localStorage, WebView storage, source files or the OS credential store.

Desktop sign-in deliberately lasts only for the app process: reopening requires
sign-in again. This avoids introducing durable credential storage in this milestone.
There are no custom URI registrations, open redirect targets or arbitrary native URLs.
Cancel invalidates the attempt; late client replies are ignored. If a session was just
issued, native cancellation attempts revocation and clears it locally. If the backend
is unreachable, that orphan server record expires normally and its credential is
not retained by the app. Failed logout does not falsely claim successful revocation.

### Future web transport and endpoints

The same user, session and Google services also support a web client. Web start sets
a random browser-binding HttpOnly cookie; callback requires that same cookie in
addition to state. Successful web login sets an opaque HttpOnly, SameSite=Lax cookie
scoped to `/api`, with Secure mandatory for HTTPS configuration. Session expiry matches
the server lifetime. Logout revokes the server session and removes its cookie.
The callback shows a fixed confirmation page; return to the client manually. No
separate web app, web redirect destination or second authentication system is created.

| Endpoint | Access / behavior |
| --- | --- |
| GET /api/health | Public/local; safe configuration flags, no database ping |
| POST /api/v1/vision/question | Existing explicit local/exact-origin image reading; no login required |
| POST /api/v1/answer | Existing explicit local/exact-origin observation reasoning; no login required |
| GET /api/v1/auth/google/start | Web sign-in start; browser-binding cookie and Google redirect |
| GET /api/v1/auth/google/callback | Google code/state callback, one-use and expiry validation |
| POST /api/v1/auth/desktop/start | Exact-origin native transaction start; secret returned only to Rust |
| POST /api/v1/auth/desktop/exchange | Exact-origin one-time exchange; requires private binding secret |
| POST /api/v1/auth/desktop/cancel | Exact-origin cancellation; requires private binding secret |
| GET /api/v1/auth/me | Optional session; public DTO or null; invalid/expired/revoked session gives safe 401 |
| POST /api/v1/auth/logout | Exact-origin server revocation and cookie removal; no-session logout is safe |

Public user DTO: id, email, email_verified, display_name, avatar_url. No Google subject,
hashes, provider credentials or database details. `optional_current_user` and
`required_current_user` are reusable dependencies. Future user-owned Context Library
and Session Preparation must use required authentication and server-side `user.id`
ownership filters; never trust a client-supplied owner ID. They are not implemented.

### Configuration and exact setup

Add these **backend-only** variables to your ignored `backend/.env`, preserving OpenAI settings:

```dotenv
DATABASE_URL=postgresql://YOUR_ROLE:URL_ENCODED_PASSWORD@YOUR_HOST/YOUR_DATABASE?sslmode=verify-full
GOOGLE_CLIENT_ID=YOUR_WEB_CLIENT_ID.apps.googleusercontent.com
GOOGLE_CLIENT_SECRET=YOUR_GOOGLE_CLIENT_SECRET
AUTH_STATE_ENCRYPTION_KEY=YOUR_LOCALLY_GENERATED_FERNET_KEY
AUTH_PUBLIC_BASE_URL=http://127.0.0.1:8000
AUTH_COOKIE_SECURE=false
AUTH_SESSION_HOURS=168
```

Blank database/Google/state-key values leave local AI functionality available and
produce an actionable configuration error on sign-in. Health distinguishes database
configured and auth configured; these flags do not claim connectivity/schema readiness.
Database failures map to safe not-configured, unavailable or schema-migration errors.
Provider/state/session errors are sanitized; no raw exceptions/secret inputs are returned.

**Neon:** create a PostgreSQL project and development branch, database `solveguide`
and dedicated role. Copy its **direct** connection string into DATABASE_URL; use TLS
(`sslmode=verify-full` recommended) and URL-encode password characters. Normal
PostgreSQL elsewhere works too. Use a distinct disposable branch/database for optional
destructive integration tests. Never run downgrade against a database containing
accounts you need. No external infrastructure was created by this implementation.

**Google Cloud:** create/select a project; configure Google Auth Platform Branding,
Audience (External/testing with your test email, or your organization's Internal
audience) and Data Access for `openid`, `email`, `profile`. Create an OAuth client of
type **Web application**, because the backend redeems the code. Add this exact
authorized redirect URI:

```text
http://127.0.0.1:8000/api/v1/auth/google/callback
```

Do not substitute localhost, a Vite URL, the Tauri origin or a custom scheme. A
JavaScript origin is not needed for this server-side redirect flow. Put the client ID
and secret only in backend/.env. For a future hosted backend, configure its exact
HTTPS callback separately and set AUTH_PUBLIC_BASE_URL and AUTH_COOKIE_SECURE=true.
Hosted deployment also needs explicit client origins/CSRF rules, HTTPS/reverse-proxy
and access controls for currently local/public AI endpoints; do not expose this
loopback development server publicly. Suppress callback query strings in proxy logs.

From `D:\solveguide-ai`, install dependencies and generate a private encryption key
locally (copy the generated value into backend/.env; never send it in chat):

### Validation, security and manual login check

Normal tests use mocked Google transport/identities, locally signed test JWTs,
service-boundary database fakes and PostgreSQL-dialect migration rendering. They
never contact Google or depend on Neon and do not claim real PostgreSQL concurrency
or live OAuth proof. The opt-in `test_real_postgresql_roundtrip_and_constraints`
requires both TEST_DATABASE_URL and ALLOW_TEST_DATABASE_RESET=1; it checks actual
upgrade, metadata consistency, constraints, downgrade and upgrade back to head on
a dedicated disposable database. Without those variables it is skipped.

Auth requests are bounded to 4 KiB, require exact allowed Origin and JSON on POST,
and have explicit timeouts. Cookie credentials are allowed only on auth CORS routes,
never wildcard origins. Vision/answer remain credential-free. No secret/token/query
payload logging, SQL echo or provider token persistence. The only CSP image addition
is `https://lh3.googleusercontent.com` for optional Google avatars, with no referrer.
Pointer Light, focus, themes, capture and native watcher exclusions are preserved.

After configuration/migration, restart backend and desktop. Open Settings, select
Sign in with Google, complete Google's login **yourself** in the system browser and
return to SolveGuide. Verify display name/email/avatar, then Sign out and confirm
signed-out state. Repeat manually if needed to verify an existing account reuses
the user row. Check browser denial/cancel and app Cancel sign-in; no error should
break capture/read/recommend. Real Google login is intentionally a joint manual test.

Accounts persist identity/session metadata **only**. Captures still live in memory;
Read Question explicitly sends an image to OpenAI, while Get Suggested Answer sends

## Milestone 7: Windows screen-share privacy

Settings → Privacy → **Screen-share privacy** controls only SolveGuide's own main
top-level window. It defaults **ON** on a fresh profile and requires no account,
backend, database, migration or network call. The existing visual system, themes,
Pointer Light and accessible Settings controls are preserved.

`src/privacy/` owns the typed client/controller; `PrivacySettings.tsx` renders the
preference separately from the effective native state. Main-window-only Tauri
commands call `src-tauri/src/privacy.rs`; the small `privacy/windows.rs` adapter
obtains the HWND from the existing Tauri 2.12.5 `WebviewWindow::hwnd()` method and
validates that it is a live, current-process-owned top-level window. React never
provides or receives a HWND. No broad Tauri permissions are added.

The adapter uses documented **SetWindowDisplayAffinity** with
**WDA_EXCLUDEFROMCAPTURE (0x00000011)** for ON and **WDA_NONE** for OFF, then verifies
the result with **GetWindowDisplayAffinity**. A documented local WinRT OS-version
query gates exclusion support at Windows 10 version 2004/build 19041 or newer.
This query sends no telemetry. Older Windows is reported as unsupported rather
than claiming full exclusion when only older blank-content behavior is available.
Non-Windows/browser-only previews report unsupported; no web capture protection exists.

Rust loads `.cache/preferences/screen-share-privacy.json` before the main window's
first show. The window is initially unshown only for startup ordering, affinity is
applied/verified, then normal local display proceeds even if protection fails.
Visibility is not used as the protection mechanism. Explicit ON/OFF updates apply
immediately and atomically save one boolean locally. OFF survives restart; ON does
too. Corrupt/unreadable preferences fall back to ON. Removing the local profile/cache
resets to ON. Save failure is reported separately; the current-run preference can
still apply without falsely claiming that it will survive restart.

The native contract reports capability (`supported`: true/false/unknown),
`preferenceEnabled`, `effectiveState` (enabled/disabled/unsupported/failed),
`preferencePersisted` and a sanitized issue classification. Setter, capability or
readback failures never become false success. The application stays usable, Settings
reports unconfirmed/unavailable protection and offers retry where appropriate.
Development logs contain only state/enum/numeric error classifications, never raw
HWNDs, source titles, screenshots, questions or answers.

The existing capture picker already excludes SolveGuide's own process windows;
regression coverage now verifies self/unknown-process exclusion while other process
windows remain eligible. Monitor sources remain available. Privacy never disables
Windows capture generally and is never suspended to capture a monitor or another
user-selected application. No capture-engine, AI provider or auth/database redesign
is involved. Captures remain ephemeral; toggling privacy sends/uploads no screenshot.

The pre-existing monitor-capture wrapper briefly hides/restores the companion while
taking its own monitor frame. That behavior is unchanged and independent of display
affinity. Absence from that preview alone therefore cannot prove capture exclusion;
use an external supported monitor capture/share with SolveGuide visibly open to
isolate the affinity behavior. No privacy protection is turned off in either path.

Windows affinity applies only to supported capture paths while DWM composition is
available. This is **not DRM or a guarantee against every capture method**, privileged
or unsupported capture implementations, or physical cameras. There is no injection,
hooking, other-process manipulation, process hiding, anti-proctoring or monitoring/
detection-evasion behavior. See Microsoft's
[SetWindowDisplayAffinity documentation](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-setwindowdisplayaffinity).

Automated tests use a narrow mocked platform adapter for state transitions/failures,
real local preference-file roundtrips, version-gate/source-filter logic and frontend
native-contract/UI/controller checks. They do not prove external capture exclusion.
**Actual external and monitor-capture pixel behavior remains pending visual manual
verification on the available machine**, including the capture application used.
